# U-1: ready-made builds on every merge

Players without Rust or git can now download a built `leonida.exe` and double-click it.

## The Release workflow

`.github/workflows/release.yml` runs after CI passes on a push to `main` (and by hand on `main`). It
builds `cargo build --release --locked -p leonida` on `windows-latest` and publishes a GitHub release
"Build <n>" with the tag `build-<n>` and one file, `leonida-windows-x64.zip`. The zip holds a
`leonida` folder with `leonida.exe`, `LICENSE`, `version.txt` (`build=`, `commit=`, `source=`, the
last a link to the source of that commit, as the GPL asks) and a `README.txt` telling players to
double-click `leonida.exe`. A build number that is already published is skipped, so a rerun publishes
nothing twice. A pull request that changes the workflow builds the zip as an artifact and publishes
nothing.

## The build number

`<n>` is `git rev-list --count` of the commit: the number of commits up to it. It only grows along
`main`, needs no counter stored anywhere, and anyone with a checkout can work out the same number for
the same commit, so a local build and a release can be compared without asking GitHub. The workflow
sets `RELEASE_BUILD_NUMBER` and `RELEASE_BUILD_COMMIT` for the build; `leonida version` prints them
as `version=`, `build=` and `commit=` lines, or `local` for any other build. `apps/leonida/build.rs`
marks both variables so a cached build picks up a new number. The launcher (a separate repository)
will compare its local build number with the newest `build-<n>` release and show that an update
exists; it never updates by itself.

## Double-click mode

`leonida` with no command now does what `run-gta6.ps1` does after its build step: it uses the saved
game folder if it has a `MicrosoftGame.config`, else asks for one (it can be dragged into the window)
and saves it to `leonida.toml` in the current folder, which is the exe's folder when started from
File Explorer. It offers the shader warm-up with the script's wording ([Y/n], Enter is yes), sets
`LEONIDA_LOG=warn` when it is unset and starts the game. The warm-up and the game run as
`leonida translate --warm all` and `leonida run --execute` children in the same window: the same
paths as from the script, a title that relaunches itself gets a command line it can reuse, and a
crash still leaves the parent to say what happened and wait for Enter. Every command behaves as
before.

Not handled: a title relaunch (`XLaunchNewGame`, untested live) ends the first child, so the window
says the game has closed while the relaunched one starts.

## Measured

Nothing in game: this changes how the program is built and started, not what it does once the title
runs. The unit tests cover the argument parsing, the version lines and the warm-up answer.
